# 行迹 TripForge · 旅游攻略定制

> 本次修复版请使用交付包在本机运行。原作者网站不代表本次修复版本。详见 [修复说明](docs/index.html)。

输入**目的地、天数、预算、同行人数、消费风格、行程节奏、出行月份、出发日期、兴趣偏好**，自动生成一份可执行的旅行方案：

- 逐日路线图（按片区聚类 + 最近邻排序，附每段交通方式/耗时/花费）
- **行程路线图**：SVG 示意图，每天一条路线，可单独聚焦某一天
- **三餐挂进日程**：按当天走到的片区挑餐厅，按真实人均价算钱，按当天真实空档排时间
- **逐日天气**：接 Open-Meteo，出发日期在 16 天内给精确预报，否则给近 3 年同月常年值；每一天单独标温和降水
- **导出 .ics 日历**：景点和餐点一起导出，可直接导入手机日历 / Outlook / Google Calendar
- 往返大交通与市内交通方案
- **大交通票价参考**：按里程给出飞机/高铁/火车的票价量级区间 + 官方票务查询直达链接
- **目的地实景图**：从 Wikimedia Commons 抓真实景点照片，标注作者与授权协议
- 住宿建议（按预算推导档位，按行程几何中心选位置）
- 预算分配明细与实际花费估算
- 必吃清单、实用贴士与风险提醒
- 景点门票可一键搜索该景点的实时票价与购票入口

**纯前端、零后端、零 API Key**，所有推荐逻辑在浏览器本地运行。
行程编排部分完全离线可用；实景图会去 Wikimedia Commons 取一次，天气数据会去 Open-Meteo 取一次
（都不需要 Key，取不到也不影响使用，界面会静默降级）。

已内置 **16 座城市**：成都、西安、杭州、大理、厦门、长沙、青岛、重庆、北京、丽江、
京都、曼谷、新加坡、巴黎、巴厘岛、首尔。

## 运行修复包

交付 ZIP 已带重新构建的 `dist/`。安装 Python 3 后双击 `启动旅游.bat`（Windows）或 `启动旅游.command`（macOS），或执行 `python 启动旅游.py`。浏览器打开 `http://127.0.0.1:8901/`，关闭终端即停止。浏览器模块不能通过直接双击 dist/index.html 启动。源码开发需要 Node.js 20.19+ 或 22.12+，执行 `npm ci`、`npm run dev`。

## 内置 16 城之外？用大模型生成

内置城市之外的目的地（全国任意城市），在搜索框里输入城市名后选
**「🛰️ 用 AI 生成『XX』的攻略」**，大模型会先查一份城市资料（景点、门票、住宿、
餐饮、交通），再交给**本地规则引擎**编排出逐日行程。

> **分工**：大模型只产「素材」，本地引擎管「编排」。
> 所以时间轴单调、同日 15km 上限、22:30 收工、每日夜间点 ≤1、预算偏差 <6%
> 这些硬约束全部由本地引擎保证，模型输出再乱也不会产出离谱行程。
> 同一城市多次生成结果稳定，可复现。

几个关键实现：

- **不让模型给经纬度**。模型给的坐标很不准，改为让它给「相对核心商圈的方位 + 距离」，
  再由代码转换成内部公里网格，方向和距离因此都能对上真实地理。
- **拆成两次调用**（城市+景点 / 酒店+交通+美食），单次输出量减半，避免 JSON 被 token 上限截断。
- **提示词强制紧凑 JSON**，模型默认的缩进 + 长描述会很快烧光 token。
- **识别截断**（`stop_reason=max_tokens` / `finish_reason=length`）后自动换策略重试。
- **生成结果做防御式清洗**：非法标签过滤、数值钳制、缺字段补默认值、三个住宿档次自动归档。
- **本地缓存**：生成过的城市存在 localStorage（30 天），换天数不用重新生成。
- **支持两种协议**：OpenAI 兼容 / Anthropic 兼容，可切换。

API Key 只存在浏览器 localStorage，请求由浏览器直连你自己填的接口，不经过任何中间服务器。

## 实景图与票价参考

### 目的地实景图

每份攻略顶部会按景点名去 **Wikimedia Commons** 检索真实照片，做成画廊，
同时第一张会作为头图的背景。

- 免费、无需 API Key、接口返回 `access-control-allow-origin: *`，浏览器可直连
- 图片几乎都是 CC-BY / CC-BY-SA / 公有领域，**必须署名** —— 画廊里逐张标注了作者与许可协议
- 检索做了**多词降级**（景点全名 → 去掉「景区/博物馆/公园」等后缀 → 城市名），
  命中中文景点名的概率明显更高
- 过滤掉地图、拼图、印章、logo 等噪音图，以及小尺寸和竖图
- **有图缓存 30 天，空结果只缓存 3 天**；
- **请求失败不缓存** —— 「请求失败」与「确实没找到」是两回事，
  混为一谈会让一次断网把某个城市的实景图永久钉成空白（而且界面上看不出任何异常）
- 检索失败静默降级，绝不影响攻略主流程

> 局限：靠名字检索，不能保证每张图就是那个景点本身，界面上已注明。

### 大交通票价参考

按出发地到目的地的**直线距离**给出各席别/舱位的票价**量级区间**（单程、单人），
并附官方票务查询直达链接。

> **为什么不是实时票价？**
>
> 1. 12306 没有公开 API；
> 2. `kyfw.12306.cn` 不返回 `access-control-allow-origin` 头，浏览器直连会被 CORS 拦掉（已实测）；
> 3. 它的查询端点名几周一轮换（`queryO`/`queryZ`/`queryA`…），硬编码很快失效；
> 4. 本站部署在 GitHub Pages，是纯静态站，没有后端可以代理。
>
> 所以纯前端拿不到真实票价，只能给区间 + 官方查询入口，把确认真实票价的动作交回给用户。

估算口径（单程单人，四舍五入到 5 元）：

| 方式 | 区间 |
|---|---|
| 火车硬座 | `max(8, km × 0.050)` ~ `max(12, km × 0.075)` |
| 火车硬卧 | 硬座区间 × 1.70 ~ × 1.95 |
| 高铁二等座 | `max(55, km × 0.380)` ~ `max(70, km × 0.480)` |
| 飞机经济舱 | `max(180, km × 0.550)` ~ `max(260, km × 0.950)` |

旺季（6–8 月）机票上限上浮 25%，淡季（11–2 月）上下限各降 15%。
境外目的地只给国际航班。

查询入口：火车/高铁 → 携程火车票（带出发地、目的地、出行日期），
机票 → 同程，门票 → 去哪儿。

## 出发日期、天气与日历导出

### 出发日期

左侧表单可以填「出发日期」。它不是装饰，会同时影响三件事：

- 行程里每一天标注真实日期与星期（`第 1 天 · 11 月 5 日（周四）`）
- 大交通票价的查询链接带上这个日期，查出来的就是当天的票
- 决定用精确天气预报还是常年值，也决定日历导出落在哪几天

默认给的是**今天 + 30 天** —— 留出订票的时间。

### 天气

数据来自 [Open-Meteo](https://open-meteo.com/)：免费、无需 API Key、接口返回
`access-control-allow-origin: *`，浏览器可直连。

| 出发日期 | 数据来源 |
|---|---|
| 在未来 16 天内 | 精确预报（含降水概率） |
| 更远 / 没填 | 近 3 年同月的**实测常年值**（ERA5 再分析数据） |

常年值比凭空编的「季节性建议」靠谱得多，而且不需要用户先定日期。
卡片上会写明当前用的是哪一种，不会把常年值包装成预报。

**统计口径跟着行程走**：汇总数字只用「行程实际占用的那几天」，
不会把「未来 16 天里有 3 天下雨」这种数字摆到你的三天行程上。
逐日明细里每一天都标了自己的口径（`预报` / `常年值`），混用时也一眼看得出。

> 两个坑（都实测过）：
>
> 1. archive 接口的 `end_date` **不能是未来日期**，否则整个请求直接 400。
>    所以结束日期取「今天 - 10 天」（ERA5 本身也有几天滞后）。
>    这条曾经让「常年值」这条路长期处于「请求发出去就被拒」的状态，
>    却因为界面只是不显示天气、没有任何报错，一直没人发现。
> 2. 常年值没有「降水概率」这个概念 —— 那个位置显示的是
>    **有雨日占比**（往年这 3 天里有多少天下过雨）。
>    混着显示「降水概率 100%」属于误导。
> 3. 行程跨过 16 天预报窗口时，前半段是预报、后半段是常年值。
>    这种情况卡片表头写「**预报 + 常年值**」，逐日明细里每一天仍标自己的口径。
>    汇总的「降水概率」只在**每一天都有概率数据**时才显示，
>    否则退成「有雨日占比」—— 把两天的概率均值摊到四天头上是错的。
> 4. 常年值要按行程跨越的**每一个月**去取。只按表单里的「出行月份」取，
>    跨月行程会缺掉几天数据（11-30 出发 4 天，常年值只取 12 月 → 第 1 天没数据）。
> 5. 缓存：预报 6 小时、常年值 30 天；预报的缓存 key 带当天日期，
>    免得拿 20 天前的旧预报冒充最新预报。

天气还会**反过来影响选点**：降水日占比 ≥ 40% 判定为雨季，此时室内场馆加分、纯户外景点减分，
行程自然往「下雨天也能去」的方向偏。

> 实话实说：这个倾斜的效果**受限于城市数据里到底有多少室内点**。
> 实测 16 座内置城市：晴天行程的室内点占比 16.4%，雨季只有 16.8%，16 座里只有 3 座选点发生了变化。
> 原因不是权重太弱，而是多数城市的景点库本来就没几个室内场馆（15 个景点里 1-6 个，占 7%-38%）——
> 雨季模式在 13/16 座城市里已经把能吃的室内点全吃满了。
> 所以天气卡片写的是**实际排进行程的室内点数量**，而不是笼统的「优先安排室内场馆」；
> 室内点少的城市还会额外提示「雨天调整空间有限」。

> 局限：常年值是「往年同月的平均情况」，不是某一年的实际天气；
> archive 的 ERA5 数据有几天滞后，所以取 3 年样本。

### 餐饮挂进日程

每天的行程里会插入早、午、晚三餐，规则是：

1. **按当天片区挑店**。食物数据带 `zone`（如「东关 / 回民街」），与当天景点的片区做
   分词 + 双向子串匹配；标着「全城」的餐厅对任何片区都成立，但优先级低。
2. **按实测算钱**。人均价直接取数据文件里写明的价格区间中值，
   当日餐饮 = 三餐人均之和 × 人数。**不再用「按消费风格拍脑袋的日均常量」** ——
   预算卡上的餐饮是实测出来的。
   注意算的是**三个餐次**，不是「排进日程的那几餐」：
   排不下的那顿你照样得吃，只按排出来的算会让预算凭空少几百块。
3. **按真实空档排时间**。餐点必须落在当天景点之间、**且不在路上**的空档里，
   不会出现「正在参观博物馆的同时在吃火锅」，也不会出现「正在出租车上吃午饭」。
   排不下就少排一顿，不硬塞。
4. **不天天吃同一家**。同一趟行程里用过的店会降权，优先换新店；
   同一价位的档里「吃得少的」优先，避免五天里四天吃火锅。

### 导出 .ics 日历

「每日路线」卡片右上角有「导出日历 .ics」。导出的内容包含**景点和餐点**，
时间取行程里的真实时刻。

自己实现而不是引库，是因为项目刻意保持**零运行时依赖**；
而 .ics 的核心就是「几个 VEVENT + 转义 + 折行」，不值得为它加一个依赖。

两个容易踩的坑，这里都处理了：

- **折行**：RFC 5545 规定每行不超过 75 字节，中文字符 UTF-8 占 3 字节很容易超，
  超长行会在字节边界处折断，续行以空格开头。
- **转义**：`\` `;` `,` 和换行都要转义，否则「小龙坎，火锅」会被解析器拆成两个字段。

时区用**浮动时间**（不带 `TZID`、不带 `Z`），也就是「11 月 5 日 09:00 出现在你的日历上」。
目的地和出发地往往不在同一个时区，写死 TZID 反而会把时间挪掉 1-2 小时；
对旅行日程来说，「当地 9 点开始」比「精确到 UTC 的那一秒」更有用。

## 行程路线图

每份攻略顶部有一张 **SVG 路线示意图**：每天一条折线，景点按当天顺序编号，
住宿单独一个菱形标记，底下带比例尺。

- 点「第 N 天」可以**单独聚焦那一天**，其余天淡出成虚线
- 点标记可以看景点名、片区和当天的第几站
- 零依赖、纯前端计算，SVG 直接手写

画的是**城市内部的公里网格**（原点 = 核心商圈，x 正东 / y 正北），
不是按经纬度投影的底图，所以界面上明确标了「示意路线图 · 非地理底图」。
这套坐标在手工维护的 16 城里是按真实方位布的，在 AI 城市里是由
「方位 + 距离」换算出来的 —— 所以图上的相对位置**大致符合真实地理**。

两个做砸了会很难看的细节，这里都处理了：

1. **画布尺寸要固定**。如果让 viewBox 跟着内容走，只要行程里有一个远郊点
   （成都的都江堰在 34km 外），整张卡片就会被撑到近 1000px 高、中间全是空的。
   现在画布固定，内容按统一比例尺居中，网格铺满，看起来是一块正经的底板。
2. **标签要避让**。同一片区的几个点挨得很近，标签一压就糊成一团。
   这里给每个标签按「右 → 左 → 下 → 上」试位，避开已放置的标签框和标记圆，
   实在放不下就只留编号（悬停有 tooltip）。

## 景点好评榜

主栏顶部有一份**按口碑排序的景点榜**，点一下就把景点排进你的路线 —— 不用自己排，
选完行程立刻重排，被你点中的景点在日程里带「你选的」标记。

榜单怎么排：评分打底，必去地标、命中你的兴趣偏好、当季可去都是加分项；
要预约、是远郊的略减分（不是不好，是安排起来更费劲）。
口径和引擎完全一致，不用另开一套规则。

可以按「口碑榜 / 评分 / 必去优先 / 免费优先 / 省时优先」重排，
也可以按「必去 / 免费 / 室内 / 合我口味」筛选。

两个关键设计：

1. **点选的点有优先权，但不破坏行程质量。** 点选的景点先占位置，
   其余景点围着它们编排；「同日直线距离 ≤ 15km」「远郊不与市区混排」
   「每天夜间点 ≤ 1」「每日游玩时长上限」这些硬约束一个都不破。
2. **排不下就直说。** 选了 8 个点却只给 1 天，榜单会直接提示
   「1 天排不下，建议 4 天」，行程里也会列出具体是哪几个点没能排进去、
   建议把天数调到几天。不是默默把点丢掉。

还有个「**只安排我选的**」开关，打开后行程里就只有你点的那几个点，
其余天数留白 —— 适合「我就只想在这几个点之间晃」的场景。

## 出发地覆盖

出发地不是几十个下拉选项，而是**全国 340 个地级行政区 + 任意地名实时解析**。

| 来源 | 数量 | 说明 |
|---|---|---|
| 人工维护 | 49 | 港澳台 + 热门县级市，坐标逐个核对过 |
| Wikidata 自动生成 | 291 | 全国地级市 / 地区 / 自治州 / 盟 / 特别行政区，取 P625 坐标点 |
| Photon 实时解析 | 长尾兜底 | 县级市、区县（如 义乌、昆山市），输入即查，查到后存进 localStorage |

全国坐标是一张**静态表**（`src/data/origins-cn.ts`，用 Wikidata SPARQL 一次性生成），
不依赖任何 Key、离线可用，也不给外部服务添麻烦。

界面上是可搜索组合框：

- 本地命中就直接用 —— 收录表的坐标更准，还省一次网络请求
- 本地没命中才去问 Photon，结果会带上**所属省份**方便消歧
- 名称后缀做了归一：「温州市」能命中收录的「温州」，「临夏回族自治州」能命中「临夏」
- 解析成功的城市存进 `localStorage`，下次直接命中，也能随链接分享

> 局限：Photon 是基于 OpenStreetMap 的开源地理编码器，同名城市仍可能歧义
> （裸搜「金华」会命中重庆的金华区）。所以解析结果一律附上省份让人确认，
> 而不是默默替你选一个。

## 部署到 GitHub Pages

本项目已包含 `.github/workflows/deploy.yml`，推送到 `main` 分支即自动构建并发布。

### 1. 建仓并推送

```bash
git init -b main
git add .
git commit -m "feat: 旅游攻略定制站"
git remote add origin https://github.com/<你的用户名>/<仓库名>.git
git push -u origin main
```

### 2. 开启 Pages

仓库 → **Settings** → **Pages** → Source 选 **GitHub Actions**。

之后每次 push 到 `main` 会自动发布，网址形如：

```
https://<你的用户名>.github.io/<仓库名>/
```

### 3.（可选）自定义域名

Settings → Pages → Custom domain 填入你的域名，并在域名商处加一条 CNAME 指向
`<你的用户名>.github.io`。

> `vite.config.ts` 里用的是 `base: './'`（相对路径），所以项目站点和自定义域名都不用改配置。

### 推送失败时

如果 `git push` 报 `Failed to connect to 127.0.0.1 port 7890`，说明本机 git 的全局代理
（`http.proxy`）指向了一个没在运行的代理软件。两个办法：

```bash
# 办法 A：只对本仓库绕过代理（已写进本仓库的 .git/config）
git config --local http.proxy ""
git config --local https.proxy ""
git config --local http.version HTTP/1.1

# 办法 B：全局清除失效代理
git config --global --unset http.proxy
git config --global --unset https.proxy
```

若直连 443 也超时，是本地网络到 GitHub 的链路问题，配置代理软件后再试。

### 坐标约定

**两套坐标，别搞混：**

1. **城市内部网格**：原点 `(0,0)` = 城市核心商圈中心，`x` 轴正东、`y` 轴正北，单位 km。
   用于估算市内通勤时间，不做真实地理投影。**新增城市时务必按真实方位布点**，否则交通时长会失真。

2. **真实经纬度**：`City.coordinates` 与 `OriginCity.coordinates` 存的是
   **`[纬度, 经度]`（lat, lng）**，和 `engine/geo.ts` 里 `haversine()` 的入参顺序一致。
   ⚠️ 写反了不会报错，但算出来的直线距离会偏得离谱（上海→敦煌能差出 3 倍），
   进而带偏交通方式选择、往返大交通预算和票价区间。

## 新增一个城市

1. 复制 `src/data/cities/chengdu.ts` 为 `src/data/cities/<拼音>.ts`
2. 改导出名与内容：8-16 个景点、6-8 家酒店（覆盖三个档次）、4-5 种市内交通、8-10 种美食
3. 在 `src/data/index.ts` 里 import 并加入 `CITY_PACKS` 数组
4. 如需人工校对某个出发地的坐标，在 `src/data/origins.ts` 的 `CURATED` 里补一条
   （自动生成的那 291 个不用管）

引擎会自动把它纳入搜索和推荐，无需改其他文件。

## 推荐逻辑说明

| 环节 | 做法 |
| --- | --- |
| 选点 | 标签命中加分、评分加权、最佳月份匹配、标志景点保底；**用户点选的点优先占位**，其余景点围着它们编排 |
| 聚类 | **完全链接凝聚聚类**（MERGE_DIST = 8km），避免单链聚合把远郊点串进市区簇 |
| 分天 | 同日任意两点 ≤ **15km** 硬约束；离中心 > 18km 的远郊点当天只排远郊点；远郊簇最多占 `days-1` 天 |
| 天内排序 | 从片区重心最远的点出发走最近邻路径，减少折返 |
| 时间轴 | 按 `bestTime`（上午/下午/晚间）落到对应时段，**路上时间计入**（不会出现「10:00 结束 A、10:00 开始 B」），自动避开饭点；最晚 22:30 收工 |
| 「共 X h」 | **实际游玩时长 + 路上时间**（不含吃饭与休息）。用实际排出的时长而不是景点的名义时长 —— 被 22:30 截断的景点只玩了实际那么久，按名义算最多虚高 3 小时，还会误触发「体力透支」告警 |
| 夜间配额 | 每天最多 1 个夜间景点，避免「连续三晚夜市」 |
| 交通 | 按距离选步行/骑行/地铁/公交/打车，用「时间 vs 花费」加权平衡；**大交通文案与票价列表的首选方式用同一个 800km 阈值**，不会出现「高铁为主」但列表第一条是飞机 |
| 住宿 | 预算 → 档次（<320 经济 / <780 舒适 / 高端），再按行程几何中心筛位置 |
| 天气 | 降水日占比 ≥ 40% 判为雨季：室内场馆加分、纯户外减分；实际效果受城市室内点数量限制，卡片按实际排入数量说话 |
| 路线图 | 内部公里网格投影，固定画布 + 统一比例尺 + 内容居中；标签按右/左/下/上依次试位避让 |
| 餐饮 | 按当天片区挑店（分词 + 双向子串匹配），早餐取最便宜的正餐以外、午餐取中间、晚餐取最贵；全程用过的店降权 |
| 预算 | 按消费风格分配比例；住宿 = 档位 × 晚数、门票与**餐饮** = 行程实际合计（实测口径）；**往返大交通计入估算**，超支告警与预算同口径 |
| 硬约束 | 同日 ≤15km、每天点数 ≤5/3/2、每天游玩时长 ≤11/8.5/6 小时、每晚 ≤1 个夜间点、22:30 收工 —— 全部有回归断言兜底 |
| 外部输入 | URL 参数（天数 / 预算 / 人数 / 风格 / 节奏 / 出发日期）全部按**整数 + 区间**校验，引擎边界再校验一次 —— 非整数天数会让 `Array.from({length: 3.5})` 与循环边界对不上，直接白屏 |

> 行程质量优先于景点数量：实在排不进当天的点会被直接放弃，不硬塞，允许个别空白天。

## 可选：接入大模型

不接也能用——默认全靠本地规则引擎。两种用途：

1. **任意城市生成**（内置 16 城之外）：让模型查一份城市资料，再由本地引擎排行程
2. **出行提示**：为已排好的行程补一段更贴合的提示

填入自己的接口配置后即可生效，Key 只存在浏览器 `localStorage`，不会发给任何第三方：

- **接口协议**：OpenAI 兼容 / Anthropic 兼容（可切换）
- **接口地址**：填到 `/v1` 即可
- **模型**：填具体模型名
- **Key**：填自己的密钥

大模型只负责素材与文案，**不允许编造事实**（票价、开放时间以数据文件与官方公告为准）。
